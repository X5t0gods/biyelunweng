## 1 引言

### 1.1 编写目的

本文档对「基于 Django 的中小型社区超市销售管理系统」的功能需求、数据需求、非功能性需求与验收标准作出完整、无二义的描述，作为后续概要设计、详细设计、编码实现、系统测试与项目验收的统一依据。本文档面向三类读者：项目开发人员（据此进行设计与编码）、测试人员（据此编写测试用例）、指导教师与答辩评委（据此审查需求分析的完整性与合理性）。

### 1.2 项目背景

中小型社区超市是城市零售体系中最贴近居民的业态，具有商品品类少、交易频次高、单笔金额小、营业时间长、从业人员流动频繁等特点。这类门店的信息化水平普遍偏低，大量店铺仍依赖纸质账本或通用电子表格管理进货与销售，存在以下突出矛盾：

一是**进销存数据割裂**。进货记录在供货商送货单上，销售记录依赖收银条，库存靠人工盘点，三者互不关联，店主难以实时掌握真实的库存数量与资金占用情况。

二是**缺货与积压并存**。缺少安全库存预警机制，畅销品断货后才被动补货，滞销品长期占用货架与资金，商品过期损耗难以追溯。

三是**结算效率与差错问题**。手工计算金额、折扣和找零速度慢、易出错，高峰时段排队明显；会员折扣、积分、储值余额等营销手段依赖人工记忆，难以准确核销。

四是**经营决策缺少数据支撑**。店主无法快速获知哪些商品好卖、哪些时段客流集中、毛利水平如何，采购与促销基本凭经验判断。

五是**责任追溯困难**。多个班次共用收银台与后台账号，商品变价、库存调整、订单作废等操作缺乏留痕，出现差异时无法定位到人与单据。

基于上述背景，本课题拟设计并实现一套面向单店或小型连锁的社区超市销售管理系统，以采购进货、库存管理、前台收银、会员营销、统计报表为主线，构建业务闭环，在降低操作门槛的同时保证库存、资金与单据三者的数据一致性和可追溯性。

### 1.3 适用范围与读者

本文档适用于本系统的全部建设过程。系统定位于**单门店或 3 家以内小型连锁**的日常经营管理，覆盖商品档案管理、采购入库、库存变动、销售收银、退货处理、会员运营与经营分析七个业务域，不涉及多仓库调拨、供应链金融、电商平台对接等企业级功能。

## 2 任务概述

### 2.1 建设目标

本系统的建设目标可概括为"管得住库存、算得清账、说得明经营"三个层次：

**业务闭环目标**。实现"采购入库 → 库存增加 → 前台销售 → 库存扣减 → 退货回补 → 盘点调整"的完整闭环，任一环节产生的库存变动都经由统一入口处理并生成流水记录，做到每一件商品的数量变化都能追溯到具体单据与操作人。

**效率目标**。前台收银支持条码枪扫描录入，平均单笔交易录入时间控制在 30 秒以内；常用操作（新增商品、采购入库、会员开卡）在 3 次点击内完成，无需培训即可上手。

**管理目标**。通过安全库存预警、库存盘点、报损登记等手段将账实差异显性化；通过销售趋势、热销排行、毛利分析等报表为采购和促销决策提供量化依据；通过角色权限与操作日志实现权责分明与事后审计。

**技术目标**。采用 B/S 架构与主流开源技术栈，保证系统在普通商用计算机上即可部署运行，总成本可控，便于在同类门店中推广。

### 2.2 用户与角色

系统的使用者为超市内部员工，按职责划分为四类角色，各角色在系统中的职责与权限边界如下。

| 角色 | 典型岗位 | 主要职责 | 核心权限 |
|---|---|---|---|
| 系统管理员 | 店主 / 信息化负责人 | 系统初始化、账号与权限管理、数据维护 | 全部功能，含员工账号管理、操作日志审计 |
| 店长 | 门店经理 | 经营数据分析、订单审核与作废、员工管理 | 统计报表、员工账号、操作日志、商品与会员管理 |
| 收银员 | 前台收银 | 收银结算、订单查询、退货受理 | 前台收银、销售订单、销售退货、会员查询 |
| 库管 / 采购员 | 库管、采购 | 采购进货、库存盘点与调整、商品档案维护 | 采购进货、库存管理、商品与供应商管理 |

权限采用基于角色（RBAC）的控制策略，在视图层统一拦截：未登录用户仅可访问登录页；越权访问时系统提示"您没有该功能的访问权限，请联系店长或管理员"并跳回首页。菜单项亦按角色动态渲染，收银员等角色不会看到无权限的功能入口。

### 2.3 业务范围与边界

**系统包含的功能**：员工账号与权限管理、商品分类与档案管理、供应商管理、采购进货与入库、库存查询与盘点调整、库存预警、前台收银（POS）、销售订单管理与作废、销售退货、会员等级与档案管理、会员充值与积分、统计报表（销售 / 毛利 / 商品 / 库存）、操作日志与库存流水追溯。

**系统不包含的功能**：多仓库与门店间调拨、生鲜商品的批次与效期精细化管理、生鲜称重设备与电子价签对接、第三方支付网关真实对接（本系统仅记录支付方式）、供应商对公结算与财务总账、电商与外卖平台订单同步、移动端原生应用。上述功能可作为系统后续扩展方向，不在本次建设范围内。

### 2.5 设计与实现约束

1. **技术选型约束**：后端采用 Python + Django 框架，前端采用 Bootstrap 5 与原生 JavaScript，图表使用 ECharts 5，数据库使用关系型数据库，不得引入非关系型数据库。
2. **数据一致性约束**：任何引起库存变化的操作必须调用统一的库存变更入口，禁止绕过该入口直接修改商品库存字段；库存不允许出现负值。
3. **事务约束**：销售结算、采购入库、退货处理等涉及多表写入的操作必须在同一数据库事务内完成，任一步骤失败则整体回滚。
4. **可追溯性约束**：关键业务操作（登录、新增 / 修改 / 删除主数据、入库、结算、退货、作废、盘点、调价）必须写入操作日志；所有库存变动必须写入库存流水。
5. **时间与编码约束**：系统时间统一采用北京时间（Asia/Shanghai），全站使用 UTF-8 编码，金额统一保留两位小数并采用 Decimal 精确运算，禁止使用浮点数进行金额计算。
6. **交付约束**：系统须提供一键初始化脚本，可在全新环境中完成建表与演示数据生成，便于演示与评审。

## 3 业务需求

### 3.1 核心业务流程

#### 3.1.1 采购入库流程

采购入库是库存的唯一正当增量来源。流程上先建单、后明细、再确认入库，确认环节才真正改变库存，避免误操作直接冲抵库存。

```
[开始] 库管进入「采购进货 → 新建采购单」
   ↓
选择供应商、填写备注 → 系统自动生成采购单号（CG + 年月日 + 4 位流水）
   ↓
逐条添加采购明细：选择商品 → 录入采购数量与进价 → 自动计算小计
   ↓
（可在此阶段删除明细或整单取消，均不影响库存）
   ↓
确认入库：校验明细非空 → 逐条执行库存变更（数量为正）
   ↓
生成库存流水（类型：采购入库，记录变动前后数量、关联单号、操作人）
   ↓
采购单状态：待入库 → 已入库，写入入库时间，回算采购总额
   ↓
[结束] 写入操作日志，页面提示入库成功
```

#### 3.1.2 前台收银流程

收银是系统使用频率最高的功能，设计上要求录入快、校验严、扣减准。

```
[开始] 收银员进入「前台收银」
   ↓
扫描条码或输入名称检索 → 商品加入购物车（校验：在售状态、库存充足）
   ↓
可调整数量、移除行项、整单清空
   ↓
（可选）绑定会员：按卡号 / 手机号 / 姓名检索 → 自动应用会员等级折扣
   ↓
选择支付方式：现金 / 微信 / 支付宝 / 银行卡 / 会员余额
   ↓
点击结算 → 二次校验全部行项库存 → 校验会员余额是否充足
   ↓
事务内完成：生成销售单与明细 → 扣减库存并写流水 → 累计积分与消费额
            → 会员余额支付则扣减余额 → 按累计积分自动刷新会员等级
   ↓
[结束] 清空购物车，跳转销售单详情，写入操作日志
```

#### 3.1.3 销售退货流程

退货支持按原单部分退货，整单退完后原销售单状态置为"已退货"。

```
[开始] 收银员进入「销售退货 → 新增退货」
   ↓
输入原销售单号进行检索 → 系统列出该单可退明细（数量、已退数量）
   ↓
勾选退货商品并录入退货数量（不得超过原单剩余可退数量）
   ↓
填写退货原因 → 提交
   ↓
事务内完成：生成退货单与明细 → 库存回补并写流水（类型：退货入库）
            → 按退款比例回退会员积分、累计消费与累计积分
            → 原支付方式为会员余额的，退款原路退回储值余额
   ↓
原销售单状态：已完成 → 已退货（仅当全部明细退完）
   ↓
[结束] 写入操作日志，页面提示退款金额
```

#### 3.1.4 库存盘点与调整流程

```
[开始] 库管进入「库存查询」
   ↓
按商品名称 / 条码 / 分类筛选 → 查看账面库存与库存金额
   ↓
发现差异 → 进入「库存调整」
   ↓
选择变动类型（盘点 / 报损 / 手动调整）→ 录入变动数量（正增负减）与备注
   ↓
执行库存变更 → 生成库存流水，记录变动前后数量与操作人
   ↓
（可选）进入「库存预警」查看低于安全库存的商品及建议补货量
   ↓
[结束] 库存流水页面可按商品、类型、时间范围追溯全部变动记录
```

### 3.2 业务规则汇总

| 编号 | 规则 | 说明 |
|---|---|---|
| BR-01 | 单号规则 | 采购单 CG、销售单 XS、退货单 TH，格式均为"前缀 + 年月日 + 4 位当日流水" |
| BR-02 | 库存非负 | 任何库存变更若导致库存为负，系统抛出异常并终止操作 |
| BR-03 | 在售校验 | 已下架商品不得加入购物车、不得出现在采购明细中 |
| BR-04 | 会员折扣 | 优惠金额 = 商品合计 ×（1 − 等级折扣率），实收 = 合计 − 优惠 |
| BR-05 | 积分规则 | 本次积分 = 实收金额（向下取整）× 等级积分倍率；退货按退款比例回退 |
| BR-06 | 会员升级 | 按"累计积分"自动匹配满足门槛的最高等级，结算 / 退货 / 作废后自动刷新 |
| BR-07 | 余额支付 | 使用会员余额支付须先绑定会员，且余额不小于实收金额 |
| BR-08 | 库存预警 | 当前库存 ≤ 安全库存即视为预警；建议补货量 = 安全库存 × 3 − 当前库存 |
| BR-09 | 退货约束 | 退货数量不得超过原单该商品的剩余可退数量 |
| BR-10 | 订单作废 | 仅店长及以上可操作；作废后库存按明细回补，会员积分与储值同步回退 |
| BR-11 | 删除保护 | 已被单据引用的商品、分类、供应商等主数据不可直接删除（外键保护） |
| BR-12 | 金额精度 | 所有金额使用定点数（Decimal）存储与运算，保留两位小数 |

## 4 功能性需求

### 4.1 功能需求总览

### 4.2 登录认证与权限管理（FR-01、FR-02）

系统采用账号口令认证。用户提交账号与口令后，系统校验口令正确性及账号在职状态，校验通过后建立会话并跳转到系统首页；连续校验失败时给出明确提示但不锁定账号（单店场景，避免影响营业）。

口令不得以明文存储，须使用 Django 内置的 PBKDF2 算法加盐散列后存储。用户可在个人中心修改口令，修改时须验证原口令。用户退出登录时销毁会话，退回登录页，会话标识失效后不能通过浏览器后退重新进入系统。

权限控制采用角色判定与视图层拦截相结合的方式：每个受保护视图在执行前检查当前用户的角色，不满足要求时记录一次越权尝试并重定向至首页；前端菜单同时按角色过滤，做到"看不见也进不去"。

### 4.3 商品管理（FR-03 ~ FR-05）

**商品分类**。分类采用单层结构，包含分类编码、名称、描述与排序号。列表页需展示每个分类下的商品数量与库存总量，便于店主判断品类结构。已被商品引用的分类不允许删除。

**商品档案**。商品是系统的核心主数据，字段涵盖名称、条码（EAN-13，全局唯一）、所属分类、默认供应商、规格、单位、进价、售价、当前库存、安全库存、保质期、状态（在售 / 已下架）与备注。商品列表需支持按名称、条码、分类、状态组合检索并分页展示，每页 15 条。新增与编辑时须校验：条码不重复、售价不得低于进价、安全库存不得为负。商品支持上下架切换，下架后不参与前台收银检索，但历史单据不受影响。

**供应商**。记录供应商名称、联系人、联系电话、地址、收款账号、合作状态与备注。供应商被采购单引用后不允许删除，仅可置为"停止合作"。

### 4.4 采购进货管理（FR-06 ~ FR-08）

采购单由库管或店长创建，包含供应商、经办人、明细列表、采购总额、状态（待入库 / 已入库 / 已取消）、备注、创建时间与入库时间。

采购明细包含商品、采购数量与采购单价，小计由数量与单价自动计算，采购总额由明细汇总得出。待入库状态的采购单允许添加与删除明细、整单取消或删除，这些操作均不影响库存。

确认入库是唯一改变库存的环节：系统逐条按明细数量增加商品库存，生成对应的库存流水，将采购单置为"已入库"并写入入库时间。入库操作不可撤销，如需更正应通过库存调整或退货流程处理。采购单列表需支持按单号、供应商、状态与日期范围筛选。

### 4.5 库存管理（FR-09 ~ FR-12）

**库存查询**。以列表形式展示各商品的当前库存、安全库存、进价、库存金额与预警状态，支持按名称、条码、分类筛选，并汇总展示库存总金额。

**库存调整**。提供盘点、报损、手动调整三种变动类型，调整时录入变动数量（正数为入库、负数为出库）与备注说明。系统校验调整后库存不得为负，通过后变更库存并生成流水。

**库存流水**。记录每一笔库存变动的变动类型、变动数量、变动前后库存、关联单号、操作人与变动时间，支持按商品、变动类型与时间范围查询。库存流水为只读数据，不允许编辑或删除。

**库存预警**。列出当前库存低于或等于安全库存的全部商品，给出建议补货量，并提供一键跳转采购新建的入口。系统首页顶部需常驻显示预警数量角标。

### 4.6 前台收银（FR-13 ~ FR-16）

收银台是系统的核心交互界面，要求单页面内完成全部操作，布局分为商品检索区、购物车区与结算区。

**商品录入**。支持扫描枪输入条码自动定位商品（条码唯一匹配时直接加入购物车，多条匹配时列出候选供选择），也支持按商品名称模糊检索后点击加入。加入时校验商品处于在售状态且库存不小于购买数量，不满足时给出明确提示。页面需提供近 30 天热销商品快捷入口，减少检索操作。

**购物车操作**。可调整任一行的购买数量、移除单行或清空购物车，行小计与合计实时更新。

**会员绑定**。支持按会员卡号、手机号或姓名检索会员并绑定到当前交易，绑定后自动按会员等级折扣率计算优惠金额与实收金额，并在页面明示优惠金额。

**结算**。支付方式包括现金、微信、支付宝、银行卡与会员余额五种。选择会员余额时须校验已绑定会员且余额充足。点击结算后系统进行二次库存校验，通过后在同一事务内完成：生成销售单与销售明细、扣减库存并写入流水、累计会员积分与消费额、会员余额支付则扣减余额、按累计积分刷新会员等级、清空购物车。结算成功后跳转至销售单详情页。

### 4.7 销售订单与退货管理（FR-17 ~ FR-21）

**销售订单**。列表按销售时间倒序展示单号、会员、收银员、应收 / 优惠 / 实收金额、支付方式与状态，支持按单号、日期范围、支付方式、会员筛选并分页，同时汇总筛选结果的销售总额与毛利。详情页展示明细列表、成本与毛利、会员与积分信息。

**订单作废**。店长及以上角色可作废订单，作废后库存按明细回补，会员积分、累计积分与累计消费额同步回退，原会员余额支付的款项退回储值余额，订单状态置为"已作废"。

**销售退货**。通过原销售单号检索出可退明细，勾选商品并录入退货数量后提交，系统校验退货数量不超过剩余可退数量。退货处理在同一事务内完成：生成退货单与明细、库存回补并写流水、按退款比例回退会员积分与消费额、会员余额支付则原路退回。全部明细退完后原销售单状态置为"已退货"。

### 4.8 会员管理（FR-22 ~ FR-26）

**会员等级**。等级定义包含等级名称、折扣率（如 0.95 表示 95 折）、积分倍率与升级所需积分数。系统按会员"累计积分"自动匹配满足条件的最高等级，无需人工调整。

**会员档案**。字段包含会员卡号（唯一）、姓名、手机号（唯一）、性别、生日、等级、积分余额、累计积分、储值余额、累计消费、住址、状态与入会时间。列表支持按卡号、手机号、姓名、等级筛选并分页。

**会员充值**。录入充值金额后增加储值余额，记录操作日志。充值金额须大于零。

**会员详情**。展示会员基本信息、积分与余额、消费记录（历史销售单列表）及累计消费统计，便于客服查询。

### 4.9 统计报表（FR-27 ~ FR-31）

报表模块面向店长与管理员，默认统计区间为近 30 天，支持自定义起止日期。

**销售报表**。包含销售趋势（按日 / 按月）、商品分类销售占比、支付方式分布、营业时段分布、热销商品排行与关键指标汇总（销售总额、订单数、客单价、毛利）。报表支持导出 CSV。

**毛利报表**。按月度展示销售额、成本、毛利与毛利率，并列出毛利贡献 TOP 商品。

**商品报表**。展示商品销量排行、销售额排行与滞销商品（长期无销售且库存偏高）清单。

**库存报表**。展示库存总金额、分类库存分布、预警商品数量与占比、库存周转情况。

所有报表需提供图表（折线图、柱状图、饼图）与表格两种呈现方式，图表采用 ECharts 渲染，支持响应式缩放。

### 4.10 系统首页（FR-32 ~ FR-34）

首页为登录后的默认页面，面向全体角色，展示当日与本月的核心经营指标（销售额、毛利、订单数、客单价）、近 7 日销售趋势图、分类销售占比图、库存预警提醒与最近 10 笔销售订单。首页数据须实时从数据库聚合，不使用缓存快照。

### 4.11 系统管理（FR-35 ~ FR-37）

**员工账号**。管理员与店长可新增员工账号（用户名、姓名、角色、手机号、工号、入职日期）、编辑信息、重置口令与启停账号。停用账号不能登录，但其历史操作记录与单据保留。

**操作日志**。记录操作人、所属模块、操作类型、操作详情、IP 地址与操作时间，支持按模块、操作人与时间范围查询。日志为只读，不可修改或删除。

**数据初始化**。提供命令行脚本，可在全新数据库上一键生成角色、管理员账号、商品分类、供应商、商品、会员及近 30 天的采购与销售历史数据，用于系统演示、测试与教学。

### 4.12 核心用例描述

**UC-01 用户登录**

| 项目 | 内容 |
|---|---|
| 用例编号 | UC-01 |
| 参与者 | 全体角色 |
| 前置条件 | 已拥有有效账号且账号处于在职状态 |
| 后置条件 | 建立会话，按角色渲染功能菜单，进入系统首页 |

基本事件流：

1. 用户访问系统，进入登录页。
2. 输入账号与口令并提交。
3. 系统校验账号存在、口令正确、账号在职。
4. 校验通过，建立会话并跳转至系统首页。

异常事件流：

1. 账号或口令错误 → 提示"用户名或密码错误"，保留已填账号，不建立会话。
2. 账号已停用 → 提示账号已停用，请联系管理员。
3. 未登录直接访问受保护页面 → 重定向至登录页，登录后回到原目标页面。

**UC-05 前台收银结算**

| 项目 | 内容 |
|---|---|
| 用例编号 | UC-05 |
| 参与者 | 收银员 |
| 前置条件 | 已登录且具备收银权限；购物车中至少有一件在售商品 |
| 后置条件 | 生成销售单与明细，库存扣减，会员积分与余额更新，购物车清空 |

基本事件流：

1. 收银员进入前台收银页。
2. 扫描条码或检索名称，将商品加入购物车（系统校验在售状态与库存）。
3. 需要时调整行项数量、移除行项。
4. （可选）检索并绑定会员，系统按等级折扣率计算优惠与实收金额。
5. 选择支付方式（现金 / 微信 / 支付宝 / 银行卡 / 会员余额）。
6. 点击结算，系统二次校验全部行项库存；选择会员余额时校验余额充足。
7. 系统在同一事务内生成销售单与明细、扣减库存并写入流水、累计会员积分与消费额、按累计积分刷新会员等级。
8. 清空购物车，跳转销售单详情页并提示销售单号。

异常事件流：

1. 商品已下架 → 提示该商品已下架，不加入购物车。
2. 库存不足 → 提示商品名称与当前库存，不加入或阻止结算。
3. 未绑定会员却选择会员余额支付 → 提示先绑定会员，返回收银页。
4. 会员余额不足 → 提示当前余额，阻止结算。
5. 结算过程中任一环节失败 → 事务整体回滚，购物车与库存保持原状，提示失败原因。

**UC-06 采购入库**

| 项目 | 内容 |
|---|---|
| 用例编号 | UC-06 |
| 参与者 | 库管 / 采购员 |
| 前置条件 | 已登录且具备库存管理权限；存在合作中的供应商与在售商品 |
| 后置条件 | 采购单状态变为已入库，商品库存增加并生成库存流水 |

基本事件流：

1. 新建采购单，选择供应商并填写备注，系统生成采购单号。
2. 逐条添加采购明细（商品、数量、进价），系统自动计算小计与总额。
3. 确认入库，系统校验明细非空。
4. 系统逐条增加商品库存并生成库存流水，记录关联单号与操作人。
5. 采购单置为已入库，写入入库时间，提示入库成功。

异常事件流：

1. 明细为空即确认入库 → 提示请先添加采购明细。
2. 明细商品重复添加 → 提示该商品已在明细中，改为累加数量。
3. 入库过程失败 → 事务回滚，库存与流水均不落库。

**UC-08 销售退货**

| 项目 | 内容 |
|---|---|
| 用例编号 | UC-08 |
| 参与者 | 收银员 |
| 前置条件 | 存在状态为已完成的原销售单且尚有可退数量 |
| 后置条件 | 生成退货单，库存回补，会员权益按比例回退 |

基本事件流：

1. 输入原销售单号检索，系统列出可退明细。
2. 勾选商品并录入退货数量，填写退货原因。
3. 提交，系统校验退货数量不超过剩余可退数量。
4. 系统在同一事务内生成退货单与明细、回补库存并写流水、按比例回退会员积分与消费额、会员余额支付则原路退回。
5. 全部退完时原销售单置为已退货，跳转退货单详情并提示退款金额。

异常事件流：

1. 销售单号不存在 → 提示未找到该销售单。
2. 退货数量超过可退数量 → 提示可退上限，阻止提交。
3. 订单已作废 → 提示该订单已作废，不可退货。

**UC-11 库存盘点调整**

| 项目 | 内容 |
|---|---|
| 用例编号 | UC-11 |
| 参与者 | 库管 / 采购员 |
| 前置条件 | 已登录且具备库存管理权限 |
| 后置条件 | 商品库存按调整值变更，生成库存流水与操作日志 |

基本事件流：

1. 在库存查询中定位商品并进入库存调整。
2. 选择变动类型（盘点 / 报损 / 手动调整），录入变动数量与备注。
3. 提交后系统校验调整后库存非负。
4. 变更库存并生成流水，提示调整成功。

异常事件流：

1. 调整后库存为负 → 提示库存不足与当前库存，拒绝调整。
2. 变动数量为 0 → 提示变动数量不能为零。

## 5 数据需求

### 5.1 数据实体与关系

系统共设计 12 张数据表，实体间关系如下。

| 实体 | 说明 | 关联关系 |
|---|---|---|

### 5.3 数据量估算

按单店日均 200 笔订单、每笔 3 个行项、SKU 5000 个、会员 3000 人估算：

|---|---|---|---|
| 销售单 | 7.3 万 | 22 万 | 200 笔/天 × 365 |

三年累计数据量约 200 万行，单表最大不超过 70 万行，MySQL 8.0 在合理索引条件下可满足查询性能要求。建议对销售单的销售时间、会员字段，销售明细的商品字段，库存流水的商品与时间字段建立索引。

## 6 非功能性需求

### 6.1 性能需求

| 编号 | 指标 | 要求 |
|---|---|---|
| NFR-P1 | 登录响应 | 单用户不大于 2 秒 |
| NFR-P2 | 页面首屏 | 列表页不大于 3 秒，首页聚合不大于 3 秒 |
| NFR-P3 | 条码检索 | 收银台检索并返回商品不大于 1 秒 |
| NFR-P4 | 结算事务 | 单笔 10 行以内的销售结算不大于 2 秒 |
| NFR-P5 | 报表查询 | 30 天区间报表生成不大于 5 秒 |
| NFR-P6 | 并发能力 | 支持不少于 20 个客户端同时在线操作 |
| NFR-P7 | 数据处理能力 | 支持 5000 个 SKU、100 万条销售记录下正常查询 |

性能优化措施包括：为高频查询字段建立数据库索引；列表查询使用 `select_related` / `prefetch_related` 预加载关联对象以避免 N+1 查询；统计报表使用 ORM 聚合（`aggregate` / `annotate`）在数据库层完成汇总，避免将数据全部载入内存；列表页统一分页，单页不超过 20 条。

### 6.2 安全性需求

1. **身份认证**：口令采用 PBKDF2 加盐散列存储，禁止明文保存；口令在传输中不回显。
2. **访问控制**：所有业务视图强制登录校验；越权访问在视图层拦截并记录提示；菜单按角色动态渲染。
3. **会话安全**：启用 Django 会话机制，退出登录即销毁会话；启用 CSRF 防护，所有写操作表单与 AJAX 请求均携带 CSRF 令牌。
4. **注入防护**：全部数据访问通过 ORM 参数化查询实现，禁止拼接原生 SQL。
5. **跨站脚本防护**：模板引擎默认开启自动转义，用户输入的内容原样输出而不被当作脚本执行。
6. **审计追溯**：关键业务操作写入操作日志，包含操作人、模块、动作、详情与 IP；库存变动写入库存流水，可完整追溯。
7. **数据删除保护**：主数据被业务单据引用时禁止删除，防止历史单据失去关联对象导致账目断裂。

### 6.3 易用性需求

1. 收银台为单页面操作，全流程无需翻页；支持扫码枪直接录入，回车即提交。
2. 常用功能在 3 次点击内可达；列表页提供搜索、筛选、分页与批量操作入口。
3. 所有写操作给出明确的成功或失败提示，失败时说明具体原因（如"商品【XX】库存不足，当前 3"）。
4. 表单录入项提供合理默认值（单位默认"件"、安全库存默认 10、支付方式默认现金）。
5. 危险操作（删除、作废、入库、退货）须二次确认后方可执行。
6. 页面采用响应式布局，在 1366×768 及以上分辨率正常显示，窄屏时侧边菜单转为抽屉式。
7. 关键术语、金额、日期格式全站统一，金额统一显示两位小数与货币符号。

### 6.4 可靠性与数据一致性需求

1. **事务一致性**：结算、入库、退货、作废等涉及多表写入的操作必须在同一事务内完成，失败整体回滚。
2. **库存一致性**：库存变更必须经由统一入口，同步写入流水；系统禁止出现负库存。
3. **并发控制**：多收银员同时销售同一商品时，以数据库行级锁与事务保证库存扣减不超卖。
4. **数据可恢复**：支持数据库定期备份；误操作可通过库存流水与操作日志定位并人工修正。
5. **可用性**：系统在营业时段（7:00—23:00）的可用率不低于 99%；服务端异常时给出友好错误页而非堆栈信息。

### 6.5 可维护性与可扩展性需求

1. **分层架构**：采用 Django 的 MVT 分层与多应用模块化组织（accounts / goods / purchase / sales / member / report / core），各模块职责单一、耦合度低。
2. **代码规范**：遵循 PEP 8 规范，模型与视图方法均附中文注释与 docstring；模型字段统一使用 verbose_name 中文名。
3. **配置外置**：数据库类型与连接参数支持环境变量覆盖，便于在开发、演示、生产环境间切换。
4. **数据库可移植**：通过 ORM 抽象，可在 MySQL 与 SQLite 间切换而无需修改业务代码。
5. **可扩展性**：预留商品批次管理、多门店、支付方式扩展、短信通知等扩展点，新增功能以新增应用或模型字段的方式接入，不改动既有核心流程。

### 6.6 兼容性需求

1. 服务端支持 Windows、Linux、macOS 部署；数据库支持 MySQL 8.0 与 SQLite 3。
2. 客户端支持 Chrome、Edge、Firefox 现代浏览器的最近两个大版本；不支持 IE。
3. 输入设备兼容键盘模拟模式的扫码枪（无需驱动或专用接口）。

## 7 接口需求

### 7.1 用户界面接口

系统采用浏览器作为统一客户端，界面风格遵循以下约定：

1. 整体布局为"顶部导航栏 + 左侧功能菜单 + 右侧内容区"三段式，菜单按业务域分组（日常业务、进销存、客户与数据、系统管理）。
2. 当前所在页面对应的菜单项须高亮显示（蓝底 + 左侧色条），高亮判定按具体页面而非模块分组，避免同组页面高亮错位。
3. 列表页统一提供标题、筛选条件区、数据表格、分页控件与统计汇总；表格首行固定表头，金额列右对齐。
4. 表单页统一提供必填标识、校验错误提示、保存与取消按钮。
5. 图表统一使用 ECharts 渲染，配色与页面主色调一致，支持鼠标悬停查看数值。

### 7.2 软件接口

| 接口 | 用途 | 说明 |
|---|---|---|
| Django ORM | 数据访问 | 全系统通过 ORM 操作数据库，屏蔽底层数据库差异 |
| PyMySQL | 数据库驱动 | 以 MySQLdb 兼容模式注册，供 Django MySQL 后端调用 |
| Bootstrap 5 | 前端样式 | 通过 CDN 引入，提供栅格与组件 |
| Bootstrap Icons | 图标 | 通过 CDN 引入 |
| ECharts 5 | 图表渲染 | 通过 CDN 引入，用于趋势图、饼图、柱状图 |

### 7.3 内部数据接口

系统提供以下内部 JSON 接口，供页面异步调用：

| 接口 | 方法 | 用途 |
|---|---|---|
| /goods/api/product/ | GET | 按条码或名称检索商品，供收银台异步查询 |
| /member/api/search/ | GET | 按卡号、手机号或姓名检索会员，供收银台绑定会员 |
| /report/sales/export/ | GET | 按日期区间导出销售数据 CSV |

### 7.4 数据导出接口

销售报表支持导出 CSV 文件，文件名包含起止日期，字段包含销售单号、销售时间、会员、收银员、应收金额、优惠金额、实收金额、支付方式与状态，编码采用 UTF-8 带 BOM 以便 Excel 直接打开不乱码。
