## 一、课题背景与研究意义

### 1.1 选题背景

社区超市是城市零售体系中分布最广、与居民日常生活联系最紧密的业态之一。据行业统计，我国便利店及社区超市门店数量已超过百万家，其中绝大多数为营业面积在 100～500 平方米、员工 5～20 人的中小型门店。这类门店普遍具有以下特征：商品 SKU 数量在数百至数千之间，日均交易笔数几十到数百笔，客单价较低但交易频次高，商品周转快、保质期敏感，且通常由店主或亲属兼任采购、库管与收银等多个角色。

在实际经营中，大量中小型社区超市仍处于"手工记账 + 单机收银机"甚至"纸质台账"的管理状态，暴露出以下突出问题：

1. **销售与库存脱节。** 前台收款设备仅完成收款功能，销售数据不回写库存，店主无法实时掌握商品余量，补货靠经验和记忆，经常出现畅销品断货、滞销品积压并存的情况。
2. **数据孤岛严重。** 采购、销售、库存、会员数据分散在不同的纸质单据或相互独立的软件中，缺乏统一的业务主线，难以进行关联分析。
3. **经营决策缺乏依据。** 店主往往只能知道"今天卖了多少钱"，无法回答"哪些商品毛利最高""哪个时段客流最集中""哪些商品临近保质期需要促销"等直接关系盈利的问题。
4. **会员运营能力薄弱。** 会员信息依靠纸质登记或店员记忆，积分、储值、折扣难以准确核算，客户粘性无法有效提升。
5. **信息化成本门槛高。** 大型 ERP 或连锁零售管理系统动辄数万至数十万元，且实施周期长、操作复杂，中小门店难以承受；而通用进销存软件又往往功能冗余、流程僵化，与社区超市的实际业务流程不匹配。

基于上述背景，本课题拟设计并实现一套**成本低、易部署、易上手、贴合社区超市实际业务流程**的销售管理系统，将采购、销售、库存、会员与经营分析整合于统一平台，帮助门店实现"业务数字化、数据可视化、决策科学化"。

### 1.2 研究意义

**（1）理论意义**

本课题是典型的中小规模信息系统工程实践，涉及需求工程、面向对象分析与设计、关系数据库规范化设计、Web 应用分层架构、基于角色的访问控制（RBAC）等软件工程核心知识。通过完整经历需求分析、系统设计、编码实现、测试验证的全过程，能够将软件工程、数据库系统原理、Web 开发技术等课程的理论知识融会贯通，形成对信息系统开发方法论的系统性认识，具备一定的学术研究训练价值。

**（2）实际应用价值**

- **提升运营效率**：收银环节由扫码加购、自动算价、一键结算替代手工录入，单笔交易处理时间大幅缩短；采购入库与库存联动，避免重复盘点。
- **降低经营成本**：库存预警机制减少缺货损失与过期损耗；毛利分析帮助店主识别高贡献商品，优化商品结构与陈列资源。
- **支撑经营决策**：通过销售趋势、热销排行、分类占比、支付方式分布等多维报表，为进货计划、促销方案、营业时间调整提供量化依据。
- **增强客户粘性**：会员等级、积分累计与储值余额构成完整的会员运营闭环，提升复购率。
- **推动小微零售数字化转型**：系统采用开源技术栈，部署成本低，可复制推广至数量庞大的社区超市、便利店、农资店等小微零售主体。

## 二、国内外研究现状

### 2.1 国外研究现状

国外零售信息化起步较早。20 世纪 80 年代，沃尔玛等大型零售企业率先引入 POS（Point of Sale）系统与 EDI 电子数据交换技术，实现了销售数据的实时采集与供应链协同。90 年代，以 SAP Retail、Oracle Retail 为代表的 ERP 系统将采购、库存、销售、财务整合为一体化解决方案，并逐步引入数据仓库与商业智能（BI）技术。进入 21 世纪，随着云计算与移动互联网的发展，Shopify、Square、Lightspeed 等 SaaS 化零售平台兴起，以按需订阅、免部署的方式服务中小商户，支持多终端（PC、平板、手机）协同收银与跨渠道（线上+线下）销售。

在技术层面，国外学术界对零售信息系统的研究已从"流程电子化"转向"数据智能化"：利用关联规则挖掘（如 Apriori 算法）进行购物篮分析以指导商品陈列；利用时间序列模型（ARIMA、Prophet）进行销量预测以优化补货；利用聚类算法进行客户分群以实现精准营销。

国外方案的不足之处在于：多数成熟产品面向欧美市场的财务与税务规则设计，本地化程度不足；SaaS 模式依赖持续的网络连接与订阅费用，且数据存储在第三方平台，与国内小微商户的使用习惯和数据安全诉求存在差距。

### 2.2 国内研究现状

国内零售管理软件的发展大致经历了三个阶段：

第一阶段为**单机进销存阶段**（2000 年前后），以"管家婆""速达"等为代表，采用 C/S 架构或纯单机部署，功能聚焦于进货、销售、库存三本账，解决了"记账电子化"问题，但数据无法共享、不支持多终端协同。

第二阶段为**行业专用系统阶段**（2010 年前后），随着连锁便利店与专卖店的扩张，出现了面向特定业态的管理系统，普遍采用 C/S 或早期 B/S 架构，集成了会员管理、促销管理、配送管理等功能，但系统封闭、二次开发困难、授权费用较高。

第三阶段为**云化与移动化阶段**（2015 年至今），以"银豹""思迅天店""客如云"等为代表，采用 B/S 与移动端结合的方式，支持扫码支付、电子会员、小程序商城、多门店连锁管理，技术栈普遍转向 Java（Spring Boot / Spring Cloud）或 PHP（ThinkPHP / Laravel），前端采用 Vue、Element UI 等组件库。

在学术与教学领域，国内高校计算机类专业的课程设计与毕业设计中，涌现出大量基于 Java Web、SSM、Spring Boot 以及 Python Django 的超市管理系统实现。综合查阅相关文献，现有成果存在以下共性问题：

1. **重功能堆砌、轻业务闭环**。多数系统仅实现增删改查（CRUD），采购—入库—销售—库存联动、销售退货回补库存等关键业务链路不完整。
2. **缺乏数据分析能力**。报表模块多停留于数据列表展示，几乎没有可视化图表与毛利分析，难以体现"管理系统"的决策支持价值。
3. **权限模型简单**。多数系统仅区分管理员与普通用户两级权限，缺少面向真实岗位（店长、收银员、库管员）的细粒度权限控制与操作审计。
4. **技术选型与实际需求不匹配**。部分方案为追求"技术先进"引入分布式、微服务等重型架构，与中小门店单机或局域网部署的实际场景脱节，反而提高了部署与维护成本。

### 2.3 现有研究述评与发展趋势

综合来看，零售管理系统的技术发展趋势可概括为：**架构上从 C/S 走向 B/S 与云原生；功能上从单一进销存走向业财一体化；数据上从记录型走向分析型与智能型；交互上从 PC 端走向多端协同**。

针对中小型社区超市这一特定场景，理想的系统应当满足"三低三高"：**低部署成本、低学习成本、低维护成本，高业务贴合度、高数据价值、高可扩展性**。这正是本课题的切入点：以 Python Django 这一开发效率高、生态成熟的 Web 框架为技术底座，构建一套功能完整但不臃肿、流程贴合实际、具备可视化分析能力且可本地化部署的社区超市销售管理系统。

## 三、研究目标与主要研究内容

### 3.1 研究目标

设计并实现一套面向中小型社区超市的 B/S 架构销售管理系统，具体目标为：

1. 实现采购进货、商品档案、库存管理、前台收银、销售退货、会员管理六大核心业务的信息化管理，形成完整的业务数据闭环。
2. 实现基于角色的权限控制与操作日志审计，满足多岗位协同与责任追溯需求。
3. 实现多维度的经营数据可视化分析，包括销售趋势、分类占比、热销排行、毛利分析、支付方式分布等。
4. 系统具备良好的可用性与可维护性，界面简洁直观，普通店员经简短培训即可上岗操作；同时具备向 MySQL 迁移与功能扩展的能力。

### 3.2 主要研究内容

**（1）需求分析**。通过分析社区超市的日常经营流程，梳理采购员、库管员、收银员、店长四类岗位的业务活动，明确功能性需求（业务功能）与非功能性需求（性能、安全性、易用性、可维护性），绘制用例图、业务流程图与数据流图。

**（2）系统设计**。包括：
- 总体架构设计：采用 Django MVT（Model-View-Template）分层架构；
- 功能模块设计：划分为系统首页、商品管理、采购管理、销售管理、库存管理、会员管理、统计报表、系统管理八大模块；
- 数据库设计：完成 E-R 模型设计、关系模式转换与规范化（满足第三范式），确定 10 张核心数据表及其约束；
- 安全设计：基于角色的访问控制（RBAC）、密码加密存储、CSRF 防护、SQL 注入防护。

**（3）系统实现**。使用 Python + Django 完成后端业务逻辑，使用 Bootstrap 5 + ECharts 5 完成前端页面与数据可视化，重点实现：
- 收银台会话购物车与事务化结算（库存扣减、积分累计、会员余额扣款的原子性）；
- 采购入库驱动的库存自动变更与库存流水留痕；
- 销售退货的库存回补与订单状态流转；
- 基于 ORM 聚合查询的多维统计与 CSV 导出。

**（4）系统测试**。设计测试用例，对核心业务链路（采购入库、收银结算、销售退货、库存盘点）进行功能测试，对全站页面进行可访问性测试，验证系统正确性与稳定性。

### 3.3 拟解决的关键问题

| 关键问题 | 解决思路 |
|---|---|
| 销售/退货/盘点等多场景下库存的一致性问题 | 统一封装 `Product.change_stock()` 方法，所有库存变更经由该入口，并在数据库事务中同步写入库存流水表，保证账实相符且可追溯 |
| 结算过程的并发与数据完整性问题 | 使用 Django 的 `transaction.atomic()` 事务装饰器，将生成销售单、写入明细、扣减库存、更新会员积分与余额封装为单个原子操作；结算前二次校验库存 |
| 多岗位的权限隔离问题 | 设计基于角色的权限模型，通过自定义装饰器与 Mixin 在视图层统一拦截，并在模板层按角色动态渲染菜单 |
| 统计分析查询的性能问题 | 合理使用 ORM 的 `annotate`/`aggregate`/`values` 聚合查询与 `select_related` 预加载，避免 N+1 查询；对高频查询字段建立索引 |
| MySQL 时区表缺失导致日期统计失效 | Windows 版 MySQL 默认不导入 `mysql.time_zone_*` 表，`CONVERT_TZ()` 返回 NULL，会使 Django 的 `__date` 过滤与 `TruncDate` 聚合结果为空。本系统采用 `USE_TZ=False` + `TIME_ZONE='Asia/Shanghai'`，全部时间按本地时间处理，并在连接初始化时固定会话时区为 `+08:00`，彻底规避该问题 |
| 批量数据初始化的写入性能问题 | SQLite 逐条自动提交在 Windows 下极慢（实测超过 100 秒）。将整个初始化过程包裹在单个数据库事务中后，耗时降至 3 秒左右 |
| 易用性与学习成本问题 | 采用一致化的页面布局与表单渲染风格，关键操作提供二次确认与即时提示，收银台支持扫码枪自动提交 |

## 四、研究方法与技术路线

### 4.1 研究方法

1. **文献研究法**：查阅国内外零售信息化、进销存系统、Django Web 开发相关的学术论文与技术文档，明确研究现状与技术选型依据。
2. **需求调研法**：以典型社区超市为对象，梳理其采购、入库、上架、收银、盘点、退货、会员运营的实际作业流程，形成需求规格说明。
3. **结构化分析与设计方法**：采用自顶向下、逐层分解的方式完成功能模块划分；采用 E-R 方法进行数据库概念设计。
4. **原型迭代法**：遵循"原型—反馈—改进"的迭代开发模式，先实现核心业务闭环，再逐步完善辅助功能与可视化分析。
5. **软件测试法**：编写自动化测试脚本，进行页面可访问性冒烟测试与核心业务流程测试。

### 4.2 技术路线

- **后端框架**：Django 5.1。Django 自带 ORM、用户认证、后台管理、表单校验、CSRF 防护、分页等组件，遵循"不重复造轮子"的设计哲学，可显著提升开发效率；其 MVT 分层架构使模型、视图、模板职责清晰，便于维护与扩展。
- **开发语言**：Python 3.13。语法简洁、生态丰富，在数据处理与分析领域优势明显，便于后续扩展智能化分析功能。
- **数据库**：MySQL 8.0，存储引擎 InnoDB，字符集 `utf8mb4`（`utf8mb4_unicode_ci` 排序规则），完整支持中文与生僻字存储。连接层使用纯 Python 的 PyMySQL 驱动，并在项目入口执行 `pymysql.install_as_MySQLdb()` 适配 Django 的 MySQL 后端，避免 Windows 环境下编译 `mysqlclient` 的困扰。借助 Django ORM 的抽象，系统可通过一个环境变量在 MySQL 与 SQLite 之间切换，业务代码零改动，便于离线演示与交付。
- **前端技术**：HTML5 + CSS3 + JavaScript，Bootstrap 5 响应式栅格布局（兼容平板等终端），Bootstrap Icons 图标库，ECharts 5 数据可视化图表库。
- **开发工具**：PyCharm / VS Code、Git、Chrome 开发者工具、Django Debug Toolbar（可选）。

### 4.3 可行性分析

**（1）技术可行性。** Django 框架成熟稳定、文档完善、社区活跃，本项目所使用的 ORM 查询、事务控制、表单处理、模板渲染、用户认证等均属框架的标准能力；前端采用的 Bootstrap 与 ECharts 均为成熟的开源组件。技术风险低，可控性强。

**（2）经济可行性。** 系统全部基于开源免费技术栈，无需支付任何软件授权费用；可在普通 PC 或入门级服务器上部署，硬件投入极低；采用 B/S 架构，客户端零安装，维护成本大幅降低。对中小门店而言具有极高的性价比。

**（3）操作可行性。** 系统界面遵循主流后台管理系统的布局习惯（顶部导航 + 左侧菜单 + 内容区），操作流程与线下作业流程保持一致，如采购单"新建—添加明细—确认入库"三步法、收银台"扫码—加购—结算"三步法。收银台支持条码枪即扫即录，普通店员经半小时培训即可独立操作。

**（4）时间可行性。** 系统功能边界清晰，模块划分合理，Django 框架的开发效率较高，按照下述进度安排可在规定周期内完成。

## 五、系统总体设计方案

### 5.1 系统架构设计

系统采用 B/S 三层架构：

- **表现层（Presentation Layer）**：基于 Django Template 引擎渲染 HTML 页面，通过 Bootstrap 实现响应式布局，通过 ECharts 实现图表展示，通过 AJAX 实现收银台商品检索等局部异步交互。
- **业务逻辑层（Business Logic Layer）**：由 Django 视图（View）与表单（Form）构成，负责请求处理、权限校验、业务规则实现、事务控制与数据组装。
- **数据访问层（Data Access Layer）**：由 Django ORM 与模型（Model）构成，负责对象—关系映射、数据持久化与完整性约束，屏蔽底层数据库差异。

### 5.2 功能模块划分

系统划分为八大功能模块：

1. **系统首页（经营看板）**：今日销售额、今日毛利、今日订单数、本月累计销售额等核心指标卡片；近 7 日销售趋势折线图；分类销售占比环形图；库存预警清单；最近销售订单列表。
2. **商品管理**：商品分类维护、商品档案维护（条码、名称、规格、单位、进价、售价、库存、安全库存、保质期、供应商）、上下架管理、商品详情与库存变动追溯。
3. **采购管理**：采购单新建、明细添加、确认入库（自动生成库存流水并增加库存）、采购单取消与删除、采购历史查询。
4. **库存管理**：库存查询与库存总金额统计、库存盘点/报损/手动调整、库存流水追溯、库存预警清单（库存 ≤ 安全库存）。
5. **销售管理**：前台收银台（POS）、销售订单查询与详情、订单作废（回退库存）、销售退货（支持部分退货与整单退货，库存自动回补）。
6. **会员管理**：会员等级设置（折扣率、积分倍率、升级门槛）、会员档案维护、储值充值、消费记录查询。
7. **统计报表**：销售统计报表（趋势、分类占比、支付方式分布、热销 TOP20，支持 CSV 导出）、利润分析（月度收入—成本—毛利、商品毛利排行）、商品销售排行、库存与会员概览。
8. **系统管理**：员工账号与角色管理、密码重置、操作日志审计、个人中心与密码修改。

### 5.3 数据库设计

数据库选用 MySQL 8.0，全部表使用 InnoDB 存储引擎以支持事务与外键约束，字符集统一为 `utf8mb4`。
系统共设计 12 张核心数据表（含 Django 内置认证表共 14 张），主要表结构如下：

| 表名（模型） | 主要字段 | 说明 |
|---|---|---|
| `accounts_user` | 用户名、密码（加密）、姓名、角色、工号、手机号、入职日期、在职状态 | 员工账号表 |
| `goods_supplier` | 名称、联系人、电话、地址、收款账号、合作状态 | 供应商表 |
| `goods_category` | 名称、编码、描述、排序 | 商品分类表 |
| `goods_product` | 名称、条码（唯一）、分类ID、供应商ID、规格、单位、进价、售价、库存、安全库存、保质期、状态 | 商品表 |
| `core_stocklog` | 商品ID、变动类型、变动数量、变动前库存、变动后库存、关联单号、操作人、时间 | 库存流水表 |
| `core_operationlog` | 操作人、模块、动作、详情、IP、时间 | 操作日志表 |
| `purchase_purchaseorder` | 单号、供应商ID、经办人、总额、状态、创建时间、入库时间 | 采购单表 |
| `purchase_purchaseitem` | 采购单ID、商品ID、数量、单价、小计 | 采购明细表 |
| `sales_sale` | 单号、会员ID、收银员、应收、优惠、实收、成本、支付方式、积分、状态、时间 | 销售单表 |
| `sales_saleitem` | 销售单ID、商品ID、商品名称、数量、单价、成本单价、小计 | 销售明细表 |
| `sales_salereturn` / `sales_salereturnitem` | 退货单号、原单ID、退款金额、原因 / 商品ID、数量、单价、小计 | 销售退货表 |
| `member_memberlevel` / `member_member` | 等级名称、折扣率、积分倍率、升级积分 / 卡号、姓名、手机号、等级ID、积分、储值余额、累计消费 | 会员等级与会员表 |

各表之间通过外键建立关联，关系模式经规范化处理满足第三范式，消除了数据冗余与更新异常；在商品表条码、会员表卡号/手机号、各单据单号等字段上建立唯一约束与索引，保证数据完整性与查询效率。

### 5.4 安全设计

1. **身份认证**：采用 Django 内置认证系统，密码经 PBKDF2 算法加盐哈希存储，不以明文保存；登录失败次数不受限时可通过扩展增加验证码机制。
2. **权限控制**：基于角色的访问控制（RBAC），定义系统管理员、店长、收银员、库管/采购员四类角色；通过视图层装饰器与 Mixin 统一拦截越权请求，并在模板层按角色动态渲染功能菜单。
3. **传输与请求安全**：启用 Django CSRF 中间件防御跨站请求伪造；ORM 参数化查询从根本上杜绝 SQL 注入；模板引擎自动转义防御 XSS 攻击。
4. **操作审计**：关键业务动作（登录、新增/修改商品、采购入库、销售结算、订单作废、退货等）均写入操作日志表，记录操作人、模块、动作、详情与 IP 地址，支持事后追溯。
5. **数据一致性保障**：销售结算、采购入库、销售退货等涉及多表写入的操作均置于数据库事务中，保证原子性；库存变更统一入口，保证账实相符。

### 5.5 界面设计原则

- **一致性**：全站统一采用"顶部导航 + 左侧菜单 + 卡片式内容区"的布局，统一的表单渲染风格与按钮语义配色。
- **简洁性**：列表页突出关键字段，详情页按需分区，避免信息过载；高频操作置于首屏。
- **反馈性**：所有操作结果通过消息提示即时反馈；删除、入库、结算等不可逆操作提供二次确认。
- **可视化**：关键经营指标以数字卡片直观呈现，趋势与结构类数据以图表呈现，降低数据理解门槛。

## 六、预期成果与创新点

### 6.1 预期成果

1. 一套可运行的社区超市销售管理系统源代码（含完整数据库脚本与演示数据初始化脚本）。
2. 一份完整的毕业论文，内容涵盖需求分析、系统设计、系统实现、系统测试与总结展望。
3. 一份系统使用说明（部署手册 + 操作手册）。
4. 系统的自动化测试脚本（页面可访问性冒烟测试、核心业务流程测试）。

### 6.2 创新点

1. **面向中小门店的轻量化业务闭环设计。** 摒弃大型 ERP 的复杂审批流，将采购、入库、销售、退货、盘点抽象为符合社区超市实际作业习惯的简洁流程，实现"单据驱动库存、业务全程留痕"的完整闭环。
2. **库存统一变更入口与全程流水追溯。** 所有库存变动（采购、销售、退货、盘点、报损）统一经由封装方法处理，同步生成库存流水，使任一库存数字均可回溯到具体单据、具体时间与具体操作人。
3. **融合会员运营的收银一体化设计。** 收银台将会员识别、等级折扣、积分累计、储值支付与商品加购集成在同一界面，实现"扫码—折扣—积分—支付"的无缝衔接。
4. **面向经营决策的可视化分析。** 不仅提供销售、毛利、热销、库存等基础报表，还通过销售趋势、分类占比、支付方式分布等图表将经营状况直观呈现，并支持 CSV 导出，切实发挥数据价值。
